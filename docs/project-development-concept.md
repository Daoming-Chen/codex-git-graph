# WorkGraph 产品概念

状态：产品方向已确认，具体机制待细化。讨论日期：2026-10-26。

WorkGraph（原 Codex Git Graph）将围绕「正在做什么、已经完成什么」组织项目开发视图。Agent 在持续开发中维护工作进展，并将进展关联到代码变化、验证结果和关键决定，让用户能够跨会话继续工作、理解历史和恢复现场。

本文面向产品设计与后续实现讨论。已确认的方向是以工作项作为主要入口；下文的记录模型、自动化策略和第一版范围是设计建议，不表示现有插件已经提供这些能力。当前实现边界见[架构与安全边界](current-implementation.md)。

## 产品定位

长期开发会跨越多个会话。会话边界不能直接决定提交边界：一个功能可能经过多次会话才完成，一次会话也可能处理多个独立问题。

Git 继续承担代码版本、分支和合并的基础能力。插件负责维护工作意图与代码历史之间的联系，并帮助 Agent 判断何时保存中间状态、形成正式提交、隔离独立工作和准备集成。

用户打开项目时，应能回答以下问题：

- 当前在推进哪些工作，各自进展到哪里？
- 哪些成果已经完成，有什么代码和验证依据？
- 上次为什么选择这个方案，还有什么没有解决？
- 从哪里继续，如何找回某个开发状态？

提交图保留为查看分支、提交和差异的入口。项目开发视图中的每项成果都应能追溯到相关证据。

## 以工作项贯穿开发过程

工作项表示一个有明确目标、可以持续推进的开发事项，例如「支持按文件筛选差异」。一个工作项可以跨越多个会话并包含多个提交；一个会话也可以处理多个工作项。

建议保存的信息包括：

| 信息 | 用途 |
| --- | --- |
| 目标与完成条件 | 说明要解决什么问题，以及何时可以判断完成 |
| 进展与下一步 | 支持跨会话继续工作 |
| 阻塞与搁置原因 | 区分正在推进、无法推进和主动暂停 |
| 关键决定 | 保留方案选择及其理由 |
| 代码关联 | 关联仓库、工作目录、分支、恢复点和提交 |
| 验证记录 | 说明验证对象、结果及尚未覆盖的范围 |
| 状态依据 | 区分 Agent 判断、程序观测和用户确认 |

这些是概念字段，尚未确定存储结构和接口。分支名不能作为工作项的唯一标识；后续设计需处理分支改名、删除、合并和提交重写。

Agent 根据用户意图维护工作项。用户应能纠正归类、拆分或合并工作项，不必手工维护每一条进展。现有改动无法可靠归属时，先显示为「尚未关联的改动」。

## 区分开发过程与正式成果

建议使用三类记录，分别服务于理解过程、恢复现场和审阅成果。

| 记录 | 产生时机 | 主要用途 |
| --- | --- | --- |
| 工作记录 | 目标变化、方案选择、验证完成或出现阻塞时 | 解释进展与决定 |
| 恢复点 | 大范围修改前、切换方向前，或已有实质进展但尚未完成时 | 找回中间状态 |
| 正式提交 | 一组具有独立意义的变化完成并满足提交条件时 | 形成可理解、可审查、可回退的代码历史 |

例如，Agent 尝试三种布局，最终选择第二种并继续完善。工作记录保留选择理由，恢复点保存必要的中间状态，正式提交描述最终形成的布局变化。

恢复点在默认视图中折叠，避免淹没正式成果。可以探索用 Git 对象和专用引用保存恢复点，但具体方案尚未确定。实现前需要明确未跟踪文件、暂存状态、敏感文件、保留期限和垃圾回收的处理方式。本地恢复点不等于远程备份。

## 项目开发视图

默认按工作组织，时间线作为补充。建议设置三个主要区域：

| 区域 | 主要内容 |
| --- | --- |
| 正在进行 | 目标、最新进展、下一步和阻塞原因 |
| 已完成 | 完成的行为变化、验证结果和相关提交 |
| 暂时搁置 | 暂停原因、保留的现场和继续入口 |

工作状态与代码状态分别展示。已有提交不代表工作完成，尚未提交也不代表没有进展。「Agent 判断完成」「验证通过」「用户接受」需要分别记录；没有用户确认时，不得显示为用户已接受。

工作卡片示例：

> **按文件筛选差异 · 进行中**  
> 已实现文件列表和筛选交互。  
> 下一步：处理文件重命名后的筛选行为。  
> 验证：基础交互通过，重命名场景待验证。  
> 代码：2 个提交，另有未提交修改。

卡片中的进展应关联差异、提交、验证结果或用户决定。验证通过需要真实的验证记录，不能仅依据 Agent 的概括性描述。

优先提供三个动作：

- **继续工作**：核对当前仓库后，恢复目标、进展、关键决定和待办。
- **查看成果**：进入相关提交、差异和验证依据。
- **恢复状态**：先说明恢复对象及对当前改动的影响，再按适用授权执行。

## Agent 如何维护工作

建议采用以下循环：

1. **开始工作**：匹配已有工作项或创建新工作项，检查仓库和当前代码现场，记录基线。
2. **推进工作**：记录有意义的进展与决定，在必要节点建立恢复点。
3. **完成稳定步骤**：评估独立提交的条件，核验范围与验证结果，再执行提交。
4. **结束或切换工作**：更新进展、待办和恢复入口，不因会话结束强制提交。
5. **下次继续**：核对记录与实际仓库状态，处理外部变化后恢复上下文。

用户可以在其他编辑器中修改代码、手动提交或切换分支。插件必须以实际仓库为依据更新关联，不能把自身记录当成全部事实。发现无法解释的变化时保留不确定状态，避免编造工作归属或完成结论。

## 自动提交策略

提交时机由 Agent 根据工作语义判断，执行条件由程序核验。定时器和会话结束可以触发评估，但不能直接证明代码适合提交。

建议在以下节点评估提交：

- 一个可独立描述的行为变化已经完成。
- 一个问题的修复及相应验证已经完成。
- 一个重构步骤形成了稳定、可单独回退的状态。
- 即将进入另一个独立目标，当前成果可以收口。

判断的核心是：这组变化能否清楚说明解决了什么问题，并在将来作为一个整体被理解和撤销？

提交前至少核验目标仓库与工作目录、候选改动范围、当前代码状态、项目要求和适用的验证结果。不满足正式提交条件时，保留工作记录或恢复点。

开始时的基线用于识别已有改动，但基线差异不能证明后续变化都属于当前 Agent。同一文件被用户或其他 Agent 修改时，需要核对归属；无法可靠区分时才请求澄清。禁止把整个工作目录默认视为当前工作项的提交范围。

验证结果必须对应准备提交的具体代码。测试整个工作目录成功后，只提交其中一部分，不能据此宣称该提交已经通过同样的验证。具体的候选版本验证方式留待实现设计。

## 分支与集成策略

分支围绕工作需要独立演进的程度建立，不与会话一一绑定。

| 情况 | 建议默认行为 |
| --- | --- |
| 当前工作中的小修复 | 继续使用当前工作分支 |
| 需要独立推进的功能 | 建立独立分支 |
| 可能放弃的方案实验 | 建立实验分支 |
| 多项工作需要同时保留未完成改动 | 使用独立 worktree 和分支 |
| 工作达到集成条件 | 按项目策略准备合并并验证集成结果 |

没有文本冲突不等于集成后行为正确。自动合并需满足项目验证要求、分支保护和团队规则。

建议允许用户预先设置项目级自动化范围，例如自动建立本地恢复点、自动创建本地提交、自动创建工作分支，以及满足条件后合入指定分支。远程推送与历史重写应有独立边界。策略配置不能绕过宿主权限或已有仓库约束。

## Skill 与执行服务的职责

| 部分 | 建议职责 |
| --- | --- |
| Skill | 指导 Agent 识别工作项、判断提交边界、维护进展和交接信息 |
| MCP 服务与本地存储 | 读取仓库、持久化记录、建立恢复点、核验并执行操作 |
| 项目开发视图与 Git Graph | 展示工作及其代码依据，支持检查、纠正和恢复 |

Skill 中的指令不能保证 Agent 在每次中断、退出或异常时都调用记录工具。文件和 Git 状态可以由程序观测，用户意图、完成原因和方案取舍需要 Agent 主动记录。

宿主生命周期事件与后台运行能力需要专项验证。在没有可靠触发机制之前，第一版应采用「调用时记录、下次进入时核对与补齐」的边界，不承诺安装后自动捕获全部开发过程。

执行接口应围绕准备提交、核验候选、保存恢复点和更新工作状态等明确动作设计。需要处理状态过期、重复调用、进程重启、并发写入和操作结果未知，避免重复提交或错误覆盖。

现有架构文档描述的模型入口主要用于打开面板，Git 写操作由面板调用。面向 Agent 的自动化工具及授权方式需要单独设计，不能假定现有面板接口已提供完整自动化能力。

## 第一版建议范围

第一版围绕「识别工作 → 持续记录 → 保存稳定成果 → 跨会话继续」形成完整闭环。

优先实现：

1. 项目级启用与自动化范围配置。
2. 工作项创建、续接、进展更新与归属纠正。
3. 必要的恢复点，以及范围明确的本地提交。
4. 工作项与提交、差异、验证结果的关联展示。
5. 再次进入项目时核对实际仓库，并提供继续工作入口。

自动整理分支、远程推送、复杂自动合并和多人同步可在后续阶段扩展。存储格式、工具名称、默认策略和页面布局尚未冻结。

### 验收场景

| 场景 | 期望结果 |
| --- | --- |
| 同一功能跨多次会话开发 | 续接同一工作项，保留进展和决定，不按会话强制提交 |
| 一次会话处理两个独立问题 | 工作和代码范围能够区分，允许用户纠正关联 |
| 存在用户预先修改的文件 | 不将其默认纳入 Agent 提交 |
| 中途暂停或异常退出 | 再次进入时识别实际状态，不将缺失记录解释为已完成 |
| 用户在外部提交或切换分支 | 展示并核对外部变化，不使用过期记录继续写入 |
| 验证对象与提交候选不同 | 不将已有验证结果直接标为候选已通过 |
| 重复请求或操作结果未知 | 核对实际结果，避免盲目重复执行 |
| 用户隔几天继续开发 | 能理解目标、已有成果、剩余问题和代码位置 |

产品效果应围绕继续工作的成本、历史的可理解性、归属准确性和恢复可靠性评估，不以提交数量衡量进展。

## 已确认的命名与视觉方向

产品名称为 WorkGraph，面向用户的核心对象是工作的进展，Git 继续作为底层代码版本管理能力。现有 GitGraph UI 是视觉基准：延续配色、深浅主题、字体层级、信息密度、图与文字行的对齐方式，以及详情和差异查看的交互习惯。新增工作视图应复用现有视觉体系，不另起一套卡片看板风格。

本轮更名覆盖产品显示名称。仓库地址、npm 包名、插件安装标识与目录、MCP 工具和资源标识、偏好存储键保持兼容；这些技术标识的迁移需单独制定方案。当前版本仍是 Git 功能，不能将 WorkGraph 名称理解为工作项自动化已经交付。

## 首页组织方式的修订建议

结合后续界面讨论，建议将「正在进行、已完成、暂时搁置」作为筛选和状态标记，替代前文所述的固定区域。默认视图采用带关系线的工作列表，详情区域展示进展与依据；展开工作查看关键事件和关联提交，并可切换到真实 Git 图。此建议尚待原型验证。

工作拆分、工作依赖和 Git 提交父子关系有不同语义，不使用同一种无标注连线混合表示。工作与提交可能交错关联，不能直接把一项工作压缩成 Git 图上的单个提交节点。没有明确关系的工作独立展示，不为形成树状结构虚构连线。

## 实现前需要确定的边界

| 决策 | 建议默认方案 | 尚需确定的内容 |
| --- | --- | --- |
| 首页与展开层级 | 工作列表、关系提示、详情区，保留 Git 模式 | 工作排序、关系线语义、展开后是否显示事件或提交 |
| 工作生命周期 | 待开始、进行中、已搁置、已完成、已取消；阻塞作为附加信息 | 完成条件、重开规则、用户确认与 Agent 判断的区别 |
| 工作与代码关联 | 工作项有独立标识，允许关联多个会话和提交 | 混合提交、跨分支、历史重写后的关联修复 |
| 第一版管理范围 | 单个本地仓库，覆盖其多个 worktree | 项目跨仓库和多人同步是否明确延后 |
| 自动化授权 | 项目级启用，分别配置恢复点、本地提交、分支与集成 | 默认开启哪些动作，结果未知时如何停下并核对 |
| 触发与恢复 | Agent 调用时记录，再次进入时核对现场 | 宿主事件的实际可用性、异常退出后的恢复能力 |
| 数据持久化 | 保存关键事件并生成当前摘要，证据关联具体版本 | 保存位置、备份迁移、保留期限、并发与重复调用 |

这些建议用于下一轮讨论，尚未冻结为实现规格。应先确定最小完整场景及边界，再分解实现任务。
